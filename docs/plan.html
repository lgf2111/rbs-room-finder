RBS Room Finder — Product Plan

A Chrome Manifest V3 extension that replaces SIT's room-booking site (rbs.singaporetech.edu.sg) with a modern, dense, dark UI codenamed Nova. It drives the site's own search API and native form; it never books anything by itself and never invents data. The whole app ships as one bundled IIFE mounted inside a shadow root, with ?nova=0 as a clean escape hatch back to the untouched native page.

2. Where we are

Nova already owns

  • The whole origin. Nova mounts on every path of the RBS origin, hides (never removes) the native DOM, and pins its shadow host over the viewport.
  • Client routing over the History API: nav pushes real RBS paths; Back/Forward and deep links work; the shell never remounts.
  • Honest unmapped screens for routes without a data API — they name the page and the missing endpoint and reveal the native page; no fabricated content.
  • Session-expiry passthrough: Nova never takes over /Home/ErrorPage or /Account/Login, and the board shows a dedicated "session expired" state when an availability POST answers with the error page as HTML.
  • Robust filters: multi-source option discovery (id, same-named select, select2 wrapper), a bounded cascade nudge, and a self-reporting diagnostics line.
  • Photo cache in chrome.storage.local: harvest-on-render, cache-first render, and a one-shot "Load room photos" action.
  • Multi-slot cart: click / shift-range / cmd-add / click-to-remove, with per-line windows and a running total.

Still native or placeholder

Two things are deliberately not done, and Nova is honest about both:

  • Booking itself. The reservation endpoint is not mapped. The cart's Confirm button stays disabled with a visible note; the only booking path today is the native handoff (select the native card, scroll the action bar into view, let the user confirm). Nova never clicks a native submit/confirm.
  • The Dashboard (/DHB001/DHB001Page) still renders the honest "not mapped" screen, pending recon of its data source.

Owner decisions now in effect: User Guide / FAQ / Support are re-rendered inside Nova (sanitised same-origin fetch, no page scripts executed); Support Booking is interactive (reservations table parsed into a Nova table with per-row handoff actions and a New-booking action); and non-bookable / non-permitted rooms are filtered out everywhere (owner: "if it cannot be booked it should not even be showing up"), with a quiet "N hidden (not bookable)" note on the status line.

Everything else on the search board (skeleton rows, single-flight slot fill, generation counter, per-room cache, hour-block dividers on the :30 boundary) is live and measured.

3. Architecture

MV3 content script, injected in order on the RBS origin:

  1. content/native.js — pure data/parse/queue layer. Parsers, payload builders, the single-flight slot queue, axis helpers. 36 Node tests depend on it; it is frozen (never edited by feature work).
  2. content/panel.js — the legacy vanilla panel, still reachable via ?nova=0; defines window.__rbsBridge. Treated as legacy, not grown.
  3. content/nova.bundle.js — React 18 + shadcn/ui (Radix) + Tailwind, compiled by esbuild into one classic IIFE. Renders into a shadow root (#rbs-room-finder-host); Tailwind is injected as a <style> inside that root; Radix portals render into #nova-portal inside the shadow root.

No runtime ESM, no CDN, no remote code, no eval/new Function. Permissions are fixed: storage + the RBS host permission — never more.

The two measured endpoints are same-origin POSTs with a fresh __RequestVerificationToken: POST /SRB001/SearchSRB001List (rooms, ~1.8–2.3 s) and POST /SRB001/GetTimeSlotListByresidNdatetime (slots for one room, ~2.1–2.2 s). The server serialises per session, so exactly one slot request is in flight at a time — never Promise.all.

Local harness on 127.0.0.1:8787 serves a stub RBS with the real control ids and select shapes. Variants exercised in verification: ?slow=1 (options populate 1.2 s after load), ?novalues=1 (selects present, no real options → diagnostics path), /__expire (both JSON endpoints answer with the error page as HTML at 200), and /Home/ErrorPage (the real session dialog markup).

The rule: every claim is a measured number — rows, cells, per-state cells, option counts, POST counts — read from the shadow root in the harness, with a screenshot for every visual claim.

4. Roadmap

Fewer, bigger phases (owner preference), ordered so the site pages come first — a coherent shell across the whole origin before deeper booking and search work.

Dashboard (/DHB001/DHB001Page), Support Booking (/SPT001/SPT001Page), User Guide (/Home/UserGuidePage), FAQ (/Home/FAQPage) and Support (/Home/SupportPage) all live under one dark Nova shell with real nav — each page re-rendered in Nova where decided, honest "not mapped" only where no data source is known yet (Dashboard).

Any invented content; a mapped cancel endpoint for Support Booking (handoff-only until captured); editing content/native.js.

Goal

In scope

  • Reserve/confirm with a verify step that reads the server's answer verbatim.

Out of scope
Auto-confirming without the verify signal; bulk/recurring booking; anything that bypasses the user's explicit confirm.

  • server response shown verbatim (no paraphrase, no invented success)
  • every reservation is cancellable; cancel verified against the site

The booking capture (blocking); whether booking is one POST or a multi-step wizard; anti-forgery/quota rules.
Top risk
Double-booking or a false "booked" claim — the highest-consequence failure in the product.

7. Verification ritual

  1. Deterministic build — npm run build; rebuilding the same checkout is byte-identical. The stamp is a content id (sha256 over the sorted build inputs) plus HEAD's committer date, so it never depends on wall-clock time or a moving HEAD sha.
  2. node --check content/nova.bundle.js — the bundle parses.
  3. node --test tests/ — 36/36 on the frozen data layer.
  4. Harness assertions — inject native.js → panel.js → nova.bundle.js on 127.0.0.1:8787, read the shadow root, assert counts (rows, cells, per-state, option counts, POST counts).
  5. Screenshot every visual claim.
  6. Owner reload of the unpacked extension on the real site.

"Which build am I on?" — one line in the console: window.__rbsBuild → { sha, builtAt }, mirrored in the status-bar stamp and on the help screens.
